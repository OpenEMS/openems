This page describes what data the **Excel export** of the web interface contains, how it depends on the selected period and what other ways there are to get data out of OpenEMS as a file or text.

[#sec-the-excel-export]
== The Excel export

[#sec-where-to-find-it]
=== Where to find it

* **History, energy overview:** Button “Download as Excel file” (in the old interface directly on the energy widget).
* **New navigation:** separate export page under History, with period selection.

According to the code, the export is “temporarily unavailable” in the **smartphone app**; it only works in the browser. The file is called e.g. `+Export-edge0-01.-31.10.2026.xlsx+`.

[#sec-does-the-export-depend-on-the-displayed-period]
=== Does the export depend on the displayed period?

**Yes.** Exactly the period currently set in the history is exported (day, week, month, year or custom period):

* **Whole days** are always exported: from 0:00 on the first day to the end of the last day, in the time zone of the browser.
* If the commissioning date is known, the export starts there at the earliest.
* If “today” is selected, the export also contains the remaining quarter hours of the day; there are no values for the future yet (displayed as “-”).
* How far back you can go depends on the storage of the history. On the device, the data goes back about 15 months (see xref:user/data/history-rrd4j.adoc[History]).

A long period results in a large file: one year is around 35,000 rows.

[#sec-where-the-data-comes-from]
=== Where the data comes from

The file is not assembled in the browser, but by the system to which the web interface is connected:

* **Connected locally to the system:** The system creates the file from its own xref:user/data/history-rrd4j.adoc[history].
* **Connected via the online portal:** The backend creates the file from the data stored there (see xref:user/cloud-interfaces/backend-data-transfer.adoc[Data transfer to the backend]).

Structure and columns are the same in both cases. The values may differ slightly because the data is stored differently.

[#sec-what-the-file-contains]
=== What the file contains

The file has one worksheet “Export” with three parts.

**1. Header:** System number (only for export via the backend), time of creation, export period.

**2. Overall overview – energy amounts for the entire period (kWh):**

[cols="2*",options="header"]
|===
| Column
| Source

| Grid purchase
| `+_sum/GridBuyActiveEnergy+`
| Grid feed-in
| `+_sum/GridSellActiveEnergy+`
| Production
| `+_sum/ProductionActiveEnergy+`
| Storage charge
| `+_sum/EssDcChargeEnergy+`
| Storage discharge
| `+_sum/EssDcDischargeEnergy+`
| Consumption
| `+_sum/ConsumptionActiveEnergy+`
|===

Each value is the difference between the meter readings at the beginning and end of the period. If a value is missing, it says “not available”.

**3. General data – power per quarter hour:** one row per 15 minutes.

[cols="3*",options="header"]
|===
| Column
| Source
| Note

| Date / time
| –
| Time of the quarter hour
| Grid purchase [W] / grid feed-in [W]
| `+_sum/GridActivePower+`
| split by sign; the other column is 0
| Production [W]
| `+_sum/ProductionActivePower+`
| 
| Storage charge [W] / storage discharge [W]
| `+_sum/EssDischargePower+`
| split by sign
| Consumption [W]
| `+_sum/ConsumptionActivePower+`
| 
| State of charge [%]
| `+_sum/EssSoc+`
| 
|===

The power values are **averages over the quarter hour**, rounded to whole watts. Missing values appear as “-”. All values come from the totals of OpenEMS (component `+_sum+`); how these are created is explained on the page xref:user/basics/energy-flows.adoc[Basics].

**4. Detailed evaluation of producers, consumers and apps:** to the right of the general data, also per quarter hour. There is a separate column with its name for each matching device:

[cols="3*",options="header"]
|===
| Group
| What goes in
| Value

| Production
| PV inverters, meters of the type “production”, PV inputs of hybrid inverters
| Power [W]
| Consumption
| Meters of the type “consumption”, charge points, heat controls (e.g. heating elements), emergency power meters
| Power [W]
| Dynamic electricity tariff
| every tariff component, provided that price control is set up
| Price per quarter hour in the sub-unit of the currency per kWh (e.g. ct/kWh)
|===

* The following do **not** appear as a separate column: grid meters, meters of the type “production and consumption”, groups of charge points and groups of PV inverters.
* The detail values are **already included in the overall overview**. The file also points this out. If you add them up and add them to the total, you count them twice.
* The electricity price is the price with which xref:user/storage-control/time-of-use-tariffs.adoc[price control] calculated in the respective quarter hour. With several tariff components, all columns show this one price.

[#sec-what-to-watch-out-for]
=== What to watch out for

* **Sum of the quarter hours ≠ overall overview:** If you convert the power values into energy (watts × 0.25 h), you do not get exactly the overall overview. It comes from the meter readings, the time series from averages. The values differ particularly for the storage: the energy totals measure on the battery side (DC), the power columns on the alternating current side.
* **Negative or implausible totals** in the overall overview have the same causes as in the history, e.g. a reset meter reading (see xref:user/data/history-rrd4j.adoc[History]).
* **Tariff without price control:** For each tariff component, the export reads the price from the first price control. If a tariff component is set up but no price control, this first price control does not exist. According to the code, the export then aborts with an error and no file is created. Remedy: deactivate the tariff component or set up a price control. This has not been tried out on a system.
* The file is intended for viewing (colors, merged cells). The routes below are better suited for further processing.

[#sec-retrieving-histories-via-json-rpc]
=== Retrieving histories via JSON-RPC

Via the REST interface (port 8084, path `+/jsonrpc+`, see xref:user/external-interfaces/rest-control.adoc[Control via REST/JSON]) you can make the same queries that the web interface uses. Two prerequisites apply:

* The REST/JSON API **with write access** must be set up (`+Controller.Api.Rest.ReadWrite+`). The read-only variant rejects every call to `+/jsonrpc+` with “REST-Api is in Read-Only mode”, even pure queries.
* The user needs at least the **Owner** role. Via the web interface or the xref:user/external-interfaces/websocket.adoc[websocket], on the other hand, the Guest role is sufficient for the same queries (see xref:user/external-interfaces/json-rpc.adoc[JSON-RPC]).

With this variant and these credentials, you can also control the system and change settings (see xref:user/external-interfaces/rest-control.adoc[Control via REST/JSON]). The password should therefore be protected accordingly.

[cols="2*",options="header"]
|===
| Query
| Delivers

| `+queryHistoricTimeseriesData+`
| Values of any channels as a time series; the resolution can be selected (e.g. 5 or 15 minutes)
| `+queryHistoricTimeseriesEnergy+`
| Energy amount per channel for the entire period
| `+queryHistoricTimeseriesEnergyPerPeriod+`
| Energy amount per channel for each section (e.g. per day or month)
| `+queryHistoricTimeseriesExportXlxs+`
| the Excel file as above, Base64-encoded
|===

The dates are whole days (`+YYYY-MM-DD+`). The end date is included. The `+id+` must be a UUID.

Example: Retrieve grid, production and consumption of one day in 15-minute resolution and save as a CSV file. The tool `+jq+` takes care of the conversion.

[source]
----
curl -s -u 'x:PASSWORD' -H 'Content-Type: application/json' \
  -X POST 'http://IP-OF-THE-SYSTEM:8084/jsonrpc' \
  -d '{"jsonrpc":"2.0","id":"00000000-0000-0000-0000-000000000001",
       "method":"queryHistoricTimeseriesData",
       "params":{"fromDate":"2026-10-29","toDate":"2026-10-29",
                 "timezone":"Europe/Berlin",
                 "channels":["_sum/GridActivePower","_sum/ProductionActivePower",
                             "_sum/ConsumptionActivePower","_sum/EssSoc"],
                 "resolution":{"value":15,"unit":"minutes"}}}' \
| jq -r '.result as $r | ($r.data|keys) as $k
         | (["Time"]+$k|@csv),
           (range($r.timestamps|length) as $i
            | [$r.timestamps[$i]] + [$k[] as $c | $r.data[$c][$i]] | @csv)' \
> export.csv
----

Result: one row per quarter hour, first column time, then one column per channel. Missing values remain empty. The conversion with `+jq+` was checked on sample data, the query was not checked on a real system.

[#sec-notes]
=== Notes

* Which channels are stored in the history and for how long is on the page xref:user/data/history-rrd4j.adoc[History]. What is not stored there cannot be delivered by any export either.
* For permanent recording beyond the approximately 15 months of the device, you must retrieve the data regularly and store it yourself, e.g. daily by script with the query above.
* For current values, the read-only variants of the REST and Modbus APIs are sufficient. For histories and energy amounts via REST (JSON-RPC), the variant with write access is required, even if the retrieval itself only reads.
